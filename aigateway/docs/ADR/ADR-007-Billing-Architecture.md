## 2. Context

### 业务背景

AI Gateway 需要新增学生账号体系、按量计费和 RBAC 权限控制三大能力。PRD v1.3 定义了以下关键需求：

- Admin 可在后台创建和管理学生账号，分配额度和模型授权
- 系统在 API 调用完成后自动计算费用并扣减额度（FR-5）
- 额度不足时返回 402 Payment Required（FR-6）
- 模型定价支持峰谷计价（FR-17.1/FR-17）
- 建立完整 RBAC 权限体系，Admin 和 Student 拥有不同功能权限（FR-9 ~ FR-15）

### 技术背景

现有架构使用 Go 1.22+、PostgreSQL 15+、Redis 7+。后端采用 Controller → Service → Repository 分层架构，已实现 Auth Middleware（JWT 认证）。当前使用 pgx v5 连接 PostgreSQL，数据库已有 users、api_keys、models、providers、request_logs 等表。

现有系统中计费、权限、角色关系均为空——需要从零构建。

---

## 3. Problem

需要做出三个架构决策：

1. **计费方式**：同步扣费（在请求链路上完成）还是异步扣费（事件队列）？
2. **峰谷定价实现**：定价数据存储在数据库（可配置）还是硬编码在配置文件中？
3. **RBAC 校验方式**：在 HTTP 中间件层统一拦截，还是在 Service 层自检？

### 问题影响

| 影响方面 | 说明 |
|---------|------|
| 功能 | 计费方式决定是否能同步返回 402；定价存储决定管理灵活性；权限校验决定安全覆盖 |
| 性能 | 同步增加 API 延迟；中间件拦截增加请求处理时间 |
| 成本 | 异步需要消息队列增加运维成本；配置文件方案修改需重启服务 |
| 开发效率 | 中间件方案 vs Service 层方案对新增接口的开发效率影响 |

---

## 4. Constraints

| # | 约束 | 类型 | 说明 |
|---|------|------|------|
| 1 | 额度不足时必须同步返回 402 | 业务 | PRD FR-6 硬性要求 |
| 2 | 同一用户并发扣费不能出现负余额 | 业务 | 数据一致性 |
| 3 | 计费扣费整体 < 50ms（99%） | 性能 | PRD 非功能需求 |
| 4 | 定价可动态配置，修改后即时生效 | 业务 | PRD FR-17 |
| 5 | 所有受保护接口必须有权限校验 | 安全 | PRD FR-15 |
| 6 | Admin 可自定义角色和分配权限 | 业务 | PRD FR-10, FR-11 |

### 不可妥协的约束

- 额度不足必须同步返回 402（FR-6）
- 并发扣费不能出现负余额
- 定价动态配置即时生效（FR-17）
- 所有受保护接口必须过权限校验（FR-15）

### 可协商的约束

- 扣费耗时目标 50ms，可适当放宽到 100ms
- 权限校验粒度：功能级权限即可，不需要数据级权限

---

## 5. Options

### 决策点 1：计费方式

| # | 方案名称 | 描述 | 优点 | 缺点 | 可行性 |
|---|---------|------|------|------|:------:|
| A | **同步扣费 + 行锁** | API 响应返回前，在数据库事务中用 SELECT FOR UPDATE 锁定用户行完成扣费 | 实时性强、强一致性、可同步返回 402 | 增加 API 延迟、同一用户串行 | 高 |
| B | **异步扣费 + 事件队列** | API 先返回响应，通过消息队列异步处理扣费 | API 响应快 | 无法同步返回 402、可能出现透支、引入 MQ 依赖 | 中 |
| C | **混合模式** | 请求前先同步查询余额，请求完成后异步扣费 | 响应延迟部分降低 | 复杂、在流式场景下仍有竞态窗口 | 低 |

### 决策点 2：峰谷定价实现

| # | 方案名称 | 描述 | 优点 | 缺点 | 可行性 |
|---|---------|------|------|------|:------:|
| A | **数据库存储** | 定价表 model_pricing 中存储定价参数，Admin 后台可修改 | 可配置性强、修改即时生效 | 每次查询需查 DB（或用缓存） | 高 |
| B | **配置文件** | 定价写在 YAML/JSON 配置文件中，启动时加载 | 部署简单、性能好 | 修改需重启服务、不可动态配置 | 高 |
| C | **环境变量 + 配置中心** | 使用配置中心动态下发定价配置 | 动态下发 | 引入外部依赖、增加运维复杂度 | 低 |

### 决策点 3：RBAC 校验方式

| # | 方案名称 | 描述 | 优点 | 缺点 | 可行性 |
|---|---------|------|------|------|:------:|
| A | **中间件统一拦截** | 在 HTTP Middleware 层统一校验权限码，路由注册时声明所需权限 | 集中管理、不侵入业务、安全不漏 | 无法访问请求体内容 | 高 |
| B | **Service 层自检** | 在每个 Service 方法中手动调用权限校验函数 | 灵活、可访问业务上下文 | 代码重复、容易遗漏 | 中 |
| C | **注解式（声明式）** | 在 Handler 注册时通过结构体声明权限要求 | 声明式、与路由绑定 | Go 不支持原生注解、需绕道实现 | 低 |

---

## 6. Decision

### 决策点 1：选择【A - 同步扣费 + 行锁 FOR UPDATE】

**决策**：在请求链路上同步完成计费扣费，使用 PostgreSQL 行锁 SELECT FOR UPDATE 保证并发安全

**决策日期**：2026-07-25

**决策人**：Architect

### 决策点 2：选择【A - 数据库存储 + Redis 缓存】

**决策**：定价数据存储在 model_pricing 表中，提供 Admin 后台 CRUD 接口，查询时使用 Redis 缓存加速

**决策日期**：2026-07-25

**决策人**：Architect

### 决策点 3：选择【A - 中间件统一拦截 + 路由声明权限码】

**决策**：在 AuthMiddleware 之后增加 PermissionMiddleware，路由注册时通过 wrapper 函数声明所需权限码

**决策日期**：2026-07-25

**决策人**：Architect

## 7. Why

### 决策点 1：同步扣费 + 行锁

| 因素 | 同步扣费 + 行锁 | 异步扣费 | 说明 |
|------|----------------|---------|------|
| 满足 PRD 同步返回 402 | ✅ 完全满足 | ❌ 无法实现 | 硬性约束 |
| 数据一致性 | ✅ 强一致（ACID） | ⚠️ 最终一致 | 计费场景要求强一致 |
| 实现复杂度 | 简单（pgx 事务） | 复杂（MQ + 补偿 + 重试） | |
| API 延迟增加 | ~10-20ms | 0 | 50ms 内完全可接受 |
| 不同用户并发 | ✅ 互不阻塞 | ✅ 互不阻塞 | 行锁粒度是用户行 |

**决定性理由**：
1. **PRD 硬性要求（FR-6）**：额度不足必须同步返回 402，异步方案从根本上无法满足
2. **数据一致性**：计费是资金相关操作，必须 ACID 级别保证
3. **性能可接受**：预估缓存命中时扣费链路 ~10ms，远低于 50ms 目标
4. **实现简单**：在当前 pgx 事务框架内直接使用 SELECT FOR UPDATE，无需引入 MQ

### 决策点 2：数据库存储 + Redis 缓存

| 因素 | 数据库存储 | 配置文件 | 说明 |
|------|-----------|---------|------|
| 动态配置（FR-17） | ✅ 天然支持 | ❌ 需重启服务 | 硬性约束 |
| 可配置性 | ✅ Admin 后台可改 | ❌ 需运维操作 | |
| 查询性能 | ⚠️ 需缓存加速 | ✅ 内存访问 | 用 Redis 弥补 |
| 部署运维 | ✅ 无额外依赖 | ✅ 简单 | |

**决定性理由**：
1. **PRD 硬性要求（FR-17）**：定价必须在 Admin 后台可配置，修改后即时生效。配置文件方案需要重启服务
2. **定价变更频率极低**：适合缓存 300s TTL + 修改后 DEL 的组合策略
3. **峰谷定价需要存储时段参数**：`peak_start`、`peak_end` 等字段在数据库存储更易管理

### 决策点 3：中间件统一拦截

| 因素 | 中间件 | Service 层 | 说明 |
|------|--------|------------|------|
| 安全覆盖 | ✅ 全局自动覆盖 | ⚠️ 需手动调用 | 中间件默认对所有匹配路由生效 |
| 代码侵入性 | ✅ 无侵入 | ❌ 侵入业务逻辑 | |
| 维护性 | ✅ 集中管理 | ⚠️ 分散在各 Service | |
| 灵活性 | ⚠️ 无法访问请求体 | ✅ 可访问业务上下文 | 功能权限不依赖请求体 |

**决定性理由**：
1. **关注点分离**：权限验证是横切关注点，中间件是最自然的实现方式
2. **安全不漏**：路由注册时通过 wrapper 声明权限码，忘记声明则默认拒绝（fail-safe）
3. **复用现有模式**：已有 AuthMiddleware 模式，PermissionMiddleware 可复用同样的 context key 传递模式
4. **性能极低**：缓存命中时权限校验在微秒级

## 8. Tradeoffs

### 接受的代价

| 代价 | 影响 | 接受理由 |
|------|------|---------|
| 同步扣费增加 API 延迟 ~10-20ms | 用户体验略有下降 | 远低于 AI 模型响应时间（通常 1-5s） |
| 行锁导致同一用户请求串行 | 单用户 QPS 受限于事务处理速度 | 学生用户通常低并发 |
| 缓存不一致窗口 | 修改定价后 TTL 内可能使用旧价格 | 修改后立即 DEL，不一致窗口 < 100ms |
| 中间件无法访问请求体 | 无法实现基于请求体内容的权限判断 | 功能权限不依赖请求体 |
| 路由-权限映射表需手动维护 | 新增接口时额外配置 | 集中在一个地方配置 |

### 放弃的优势

- **放弃了异步扣费的零延迟优势**：因为 PRD 要求同步返回 402
- **放弃了配置文件的极简方案**：因为 FR-17 要求动态配置
- **放弃了 Service 层校验的上下文访问能力**：因为功能权限校验不需要业务上下文

## 9. Consequences

### 正面后果

- 计费逻辑清晰简单，ACID 事务保证数据一致性
- 定价管理灵活，Admin 可随时调整
- 权限体系结构清晰，新增接口只需在路由注册处添加权限码声明
- 中间件拦截确保安全无遗漏

### 负面后果

- 计费成为 API 主链路的一部分，需要持续关注性能
- 行锁在高并发场景下可能成为瓶颈（单用户维度）
- 需要额外维护定价缓存和权限缓存的失效逻辑

### 迁移方案

- **Migration 005**：创建 roles、permissions、role_permissions、user_model_permissions 表 + 种子数据
- **Migration 006**：创建 model_pricing、quota_transactions 表 + 修改 users 表添加 role_id、quota_balance 字段
- 登录接口返回新增 `role` 字段和 `permissions` 列表（前端需要适配）
- AuthResponse 结构体扩展添加 role 信息

## 10. Risks

| # | 风险描述 | 等级 | 可能性 | 影响 | 缓解方案 |
|---|---------|------|--------|------|---------|
| 1 | 行锁死锁（事务顺序不一致） | 中 | 低 | 高 | 始终按固定顺序访问资源：先 SELECT FOR UPDATE，再 UPDATE，再 INSERT |
| 2 | 长事务阻塞 | 中 | 低 | 中 | 保持事务简短（< 10ms），不在事务中做网络请求 |
| 3 | 缓存穿透（定价不存在或权限为空） | 低 | 中 | 低 | 空值缓存 TTL 30~60s |
| 4 | 计费精度丢失 | 低 | 低 | 高 | Go 代码中使用 int64 表示微美元，DB 使用 DECIMAL(16,6) |
| 5 | 迁移后现有 Admin 用户无角色 | 高 | 高 | 高 | Migration 006 设置默认 Admin 角色 |

## 11. Alternatives

| 方案 | 未选原因 | 未来可行性 |
|------|---------|:----------:|
| 异步扣费 | 无法满足 PRD 同步返回 402 的要求 | 中（如果改为后端对账模式可考虑） |
| 配置文件定价 | 不支持动态配置，无法满足 FR-17 | 低 |
| Service 层权限校验 | 代码重复、容易遗漏，不遵循横切关注点分离 | 低 |
| ABAC 权限模型 | 当前需求过度（仅需功能级权限），增加复杂度 | 高（如需数据级权限可叠加） |
