## 2. Context

### 业务背景

AI Gateway 需要实现按量计费功能：每次 API 调用完成后，根据模型的定价策略和实际 token 用量计算费用，并从用户账户额度中扣减。教育场景下，学生账号由 Admin 预先分配额度，API 调用需要确保：

- 实时扣费，额度不足时立即拒绝请求（返回 402）
- 并发场景下不出现负余额
- 支持普通定价和峰谷计价两种策略
- 定价可在 Admin 后台动态配置，修改后即时生效

### 技术背景

现有架构为多服务架构（API Gateway / Billing Service / Auth Service），使用 PostgreSQL 作为主数据库，Redis 作为缓存。request_logs 表已有 cost_amount 字段（`DECIMAL(18,6)`）。计费操作需要在 API 调用链路中同步完成（PRD 要求同步返回结果）。

---

## 3. Problem

需要设计一套计费与额度扣减方案，在保证数据一致性和并发安全的前提下，实现高效、准确的按量计费。

### 问题描述

核心需要解决的三个关键决策点：

1. **同步扣费 vs 异步扣费**：PRD 要求同步返回结果，但同步扣费会增加 API 调用延迟
2. **行锁（SELECT FOR UPDATE）vs 乐观锁**：如何保证并发扣费不出现负余额
3. **定价查询时机**：每次调用查 DB 还是使用缓存

### 问题影响

| 影响方面 | 说明 |
|---------|------|
| 功能 | 计费准确性直接影响用户体验和平台收入 |
| 性能 | 扣费延迟影响 API 响应时间 |
| 成本 | 方案复杂度影响开发和运维成本 |
| 数据一致性 | 并发扣费可能导致额度透支 |

---

## 4. Constraints

| # | 约束 | 类型 | 说明 |
|---|------|------|------|
| 1 | 额度不足时必须同步返回 402 | 业务 | PRD 要求，不允许异步返回 |
| 2 | 同一用户并发扣费不能出现负余额 | 业务 | 数据一致性要求 |
| 3 | 计费扣费 < 50ms（99%） | 性能 | PRD 非功能需求 |
| 4 | 定价可动态配置，修改后即时生效 | 业务 | PRD FR-17 |
| 5 | 精度 decimal(16,6) | 业务 | PRD 非功能需求 |

### 不可妥协的约束

- 额度不足必须同步返回 402（FR-6）
- 并发扣费不能出现负余额
- 定价动态配置即时生效（FR-17）

### 可协商的约束

- 扣费耗时目标 50ms，可适当放宽到 100ms

## 5. Options

### 决策点 1：同步扣费 vs 异步扣费

| # | 方案名称 | 描述 | 优点 | 缺点 | 可行性 |
|---|---------|------|------|------|:------:|
| A | 同步扣费 | API 响应返回前完成定价查询 + 费用计算 + 额度扣减 + 事务提交 | 实时性高、402 可同步返回 | 增加 API 响应延迟 | 高 |
| B | 异步扣费 | API 响应先返回，扣费异步处理 | API 响应快 | 无法同步返回 402、额度滞后、可能透支 | 中 |
| C | 混合模式 | 请求前先查询余额（同步），扣除操作异步 | 响应延迟降低 | 复杂、在流式场景下可能还是需要同步 | 低 |

### 决策点 2：行锁 vs 乐观锁

| # | 方案名称 | 描述 | 优点 | 缺点 | 可行性 |
|---|---------|------|------|------|:------:|
| A | 行锁（SELECT FOR UPDATE） | 事务内锁定用户行，其他事务等待 | 强一致性、实现简单 | 并发时锁等待、死锁风险 | 高 |
| B | 乐观锁（version 字段） | UPDATE WHERE version=old_version，失败重试 | 无锁等待 | 高并发下重试次数多、需要重试逻辑 | 高 |
| C | Redis 分布式锁 | 使用 Redis 锁控制并发扣费 | 性能高 | 可能丢失锁导致数据不一致 | 中 |

### 决策点 3：定价查询时机

| # | 方案名称 | 描述 | 优点 | 缺点 | 可行性 |
|---|---------|------|------|------|:------:|
| A | 每次查 DB | 每次 API 调用都从 model_pricing 表读取定价 | 数据实时性最高 | 每次调用增加 DB 查询开销 | 高 |
| B | Redis 缓存 + 失效策略 | 定价缓存到 Redis，修改后 DEL 缓存 | 高性能（<1ms）、实时性可接受 | 缓存与 DB 短暂不一致（<300s） | 高 |
| C | 本地缓存 + 定时刷新 | 服务启动时加载定价到内存，定时刷新 | 速度最快 | 多实例不一致、修改无法即时生效 | 中 |

## 7. Why

### 决定因素分析

#### 同步扣费

| 因素 | 同步扣费 | 异步扣费 | 说明 |
|------|---------|---------|------|
| 满足 PRD 要求（402 同步返回） | ✅ 完全满足 | ❌ 无法实现 | PRD FR-6 硬性要求 |
| 实现复杂度 | 简单 | 复杂 | 异步需要消息队列 + 补偿机制 |
| API 响应延迟 | +5~50ms | 0 | 50ms 在可接受范围内 |
| 数据一致性 | 强一致 | 最终一致 | 计费场景要求强一致 |

**决定性理由**：
1. **PRD 硬性要求**：FR-6 要求额度不足时同步返回 402，异步方案无法满足
2. **数据一致性**：计费是资金相关操作，必须强一致
3. **实现复杂度低**：同步方案在当前 Controller → Service → Repository 架构中实现简单

#### 行锁（SELECT FOR UPDATE）

| 因素 | 行锁 | 乐观锁 | 说明 |
|------|------|--------|------|
| 并发安全 | ✅ 强保证 | ⚠️ 需重试 | 高并发下乐观锁重试可能失败 |
| 锁等待影响 | ⚠️ 同一用户串行 | ✅ 无锁 | 不同用户互不阻塞 |
| 死锁风险 | ⚠️ 需注意事务顺序 | ✅ 无风险 | 按固定顺序访问资源可避免 |
| 实现复杂度 | 简单 | 中等 | 乐观锁需要重试逻辑 |

**决定性理由**：
1. **强一致性保证**：行锁确保扣费操作的原子性，不会出现负余额
2. **用户级隔离**：行锁粒度是用户行，不同用户之间完全并行，不影响整体吞吐量
3. **实现简单**：在现有事务框架内直接使用，无需额外重试逻辑
4. **场景匹配**：PRD 强调"同一账号并发扣费不出现负额度"，行锁是最直接可靠的方案

#### Redis 缓存 + 失效策略

| 因素 | 每次查 DB | Redis 缓存 | 说明 |
|------|---------|------------|------|
| 性能 | 5~10ms/次 | < 1ms/次 | 缓存显著降低延迟 |
| 实时性 | 实时 | TTL 内可能不一致 | 300s TTL + 修改后 DEL，不一致窗口极小 |
| 实现复杂度 | 简单 | 中等 | 多一层缓存管理 |

**决定性理由**：
1. **性能目标**：计费扣费整体 < 50ms，如果定价每次查 DB（5~10ms），留给业务逻辑的空间更小
2. **业务特性**：定价是低频变更数据，缓存 300s TTL 加上修改后立即 DEL，不一致窗口几乎为零
3. **缓存穿透防护**：空结果也缓存（TTL 30s），防止恶意请求穿透

### 与约束的匹配

| 约束 | 满足情况 | 说明 |
|------|---------|------|
| 同步返回 402 | ✅ | 同步扣费方案，事务回滚后立即返回 |
| 不出现负余额 | ✅ | SELECT FOR UPDATE 保证原子扣减 |
| 扣费 < 50ms | ✅ | 缓存定价（<1ms）+ 行锁事务（~10ms），预估 20~30ms |
| 定价即时生效 | ✅ | 缓存 TTL 300s + 修改后 DEL |
| decimal(16,6) | ✅ | 数据库和代码中统一使用此精度 |

## 8. Tradeoffs

### 接受的代价

| 代价 | 影响 | 接受理由 |
|------|------|---------|
| 同步扣费增加 API 延迟 ~20-30ms | 用户体验略有下降 | 50ms 以内不可感知，远低于 AI 模型响应时间（通常 1-5s） |
| 行锁导致同一用户请求串行 | 同一用户 QPS 受限于事务处理速度 | 学生用户通常低并发，Admin 用户不计费 |
| 缓存不一致窗口 | 修改定价后最多 300s 内可能使用旧价格 | 修改后立即 DEL，不一致窗口 < 100ms |

### 放弃的优势

- **放弃了异步扣费的零延迟优势**：因为 PRD 要求同步返回 402
- **放弃了乐观锁的无锁等待优势**：因为计费场景需强一致性
- **放弃了每次查 DB 的绝对实时性**：因为性能收益远大于不一致窗口的风险

---

## 9. Consequences

### 正面后果

- 计费逻辑清晰简单，易于维护
- 并发安全有数据库层保证
- 定价缓存带来显著的性能提升
- 实现与现有架构无缝集成

### 负面后果

- 计费成为 API 调用主链路的一部分，需要关注性能
- 行锁在高并发场景下可能成为瓶颈（单用户维度）
- 需要额外维护缓存失效逻辑

### 迁移方案

无迁移需求。本模块为全新功能，不涉及现有功能的改造。

## 10. Risks

| # | 风险描述 | 等级 | 可能性 | 影响 | 缓解方案 |
|---|---------|------|--------|------|---------|
| 1 | 行锁死锁（事务顺序不一致） | 中 | 低 | 高 | 始终按固定顺序访问资源：先 SELECT FOR UPDATE，再 UPDATE，再 INSERT |
| 2 | 长事务阻塞 | 中 | 低 | 中 | 保持事务简短：不在事务中做网络请求、外部 API 调用 |
| 3 | 缓存穿透（定价不存在时） | 低 | 中 | 低 | 空值缓存 TTL 30s |
| 4 | 计费精度丢失 | 低 | 低 | 高 | 统一使用 DECIMAL(16,6)，Go 代码中使用 string 传递金额避免 float 精度问题 |

| 方案 | 未选原因 | 未来可行性 |
|------|---------|:----------:|
| 异步扣费 | 无法满足 PRD 同步返回 402 的要求 | 中（如果未来改为后端对账模式可考虑） |

| 本地缓存定价 | 多实例不一致，修改无法即时生效 | 低（不推荐） |
