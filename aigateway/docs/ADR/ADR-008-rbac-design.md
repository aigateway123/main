## 2. Context

### 业务背景

AI Gateway 当前只有单一 Admin 角色，所有用户拥有相同权限。PRD 要求建立完整的权限体系，以支持：

- Admin 拥有全部管理功能权限
- Student 只能使用 API 和查看个人用量
- Admin 可自定义角色和分配功能权限
- 前端根据角色展示不同页面
- 后端所有受保护接口均需经过权限校验

### 技术背景

现有架构使用 JWT 进行身份认证（Auth Middleware），请求上下文中包含 userID 和 email。后端使用 Controller → Service → Repository 分层架构。前端使用 Vue3 开发。

现有 auth_middleware.go 中已将 userID 注入到请求上下文中，权限校验可以在此基础上扩展。

---

## 3. Problem

需要设计一套权限模型，确保 Admin 和 Student 拥有不同的功能权限，并且所有受保护接口都经过权限校验。

### 问题描述

核心需要解决的三个关键决策点：

1. **权限模型选择**：RBAC（基于角色）vs ABAC（基于属性）
2. **权限校验时机**：中间件 vs Service 层
3. **前端权限控制策略**：如何根据角色展示不同页面

### 问题影响

| 影响方面 | 说明 |
|---------|------|
| 功能 | 权限粒度直接影响功能安全 |
| 性能 | 校验时机影响每个请求的延迟 |
| 开发效率 | 权限配置方式影响新增接口的开发效率 |
| 维护成本 | 权限模型的灵活性决定了后续扩展成本 |

---

## 4. Constraints

| # | 约束 | 类型 | 说明 |
|---|------|------|------|
| 1 | Admin 和 Student 两种内置角色 | 业务 | PRD FR-9 |
| 2 | Admin 可自定义角色和权限 | 业务 | PRD FR-10, FR-11 |
| 3 | 所有受保护接口必须有权限校验 | 安全 | PRD FR-15 |
| 4 | 前端根据角色展示不同页面 | 业务 | PRD FR-14 |
| 5 | 权限校验不通过返回 403 | 安全 | PRD 非功能需求 |

### 不可妥协的约束

- 所有受保护接口必须过权限校验（FR-15）
- 内置角色不可删除（is_system 保护）
- 权限校验不通过返回 403

### 可协商的约束

- 校验粒度：功能级权限即可，不需要数据级权限
- 自定义角色数量限制：暂不限制

---

## 5. Options

### 决策点 1：权限模型选择

| # | 方案名称 | 描述 | 优点 | 缺点 | 可行性 |
|---|---------|------|------|------|:------:|
| A | RBAC（基于角色） | 角色 ↔ 权限多对多，用户关联角色 | 简单直观、管理方便、广泛使用 | 角色多了管理复杂，不支持属性条件 | 高 |
| B | ABAC（基于属性） | 基于用户/资源/环境属性动态评估 | 灵活、细粒度 | 规则复杂、评估性能开销大、维护成本高 | 中 |
| C | RBAC + ABAC 混合 | 功能权限用 RBAC，数据权限用 ABAC | 兼顾简单性和灵活性 | 两套规则引擎，复杂度高 | 低 |

### 决策点 2：权限校验时机

| # | 方案名称 | 描述 | 优点 | 缺点 | 可行性 |
|---|---------|------|------|------|:------:|
| A | Permission Middleware | 在 HTTP 中间件层统一校验 | 集中管理、不侵入业务代码 | 需要路由-权限映射表 | 高 |
| B | Service 层校验 | 在每个 Service 方法中手动调用权限校验 | 灵活、可访问业务上下文 | 代码重复、容易遗漏 | 中 |
| C | 注解/声明式 | 使用 Go 结构体注解或路由注册时声明权限 | 声明式、与路由绑定 | Go 本身不支持注解，需绕道实现 | 低 |

### 决策点 3：前端权限控制策略

| # | 方案名称 | 描述 | 优点 | 缺点 | 可行性 |
|---|---------|------|------|------|:------:|
| A | 角色路由隔离 | 根据角色（Admin/Student）加载不同的路由表 | 简单直接、安全 | 自定义角色支持困难 | 高 |
| B | 权限点路由控制 | 根据权限码列表动态过滤路由 | 灵活、支持自定义角色 | 前端需要维护权限-路由映射 | 中 |
| C | 后端返回菜单 | 后端根据权限返回可访问的菜单/路由列表 | 最安全、无需前端维护映射 | 前后端耦合度增加 | 中 |

## 6. Decision

### 决策点 1：选择【A - RBAC 基于角色】

**决策**：选择 RBAC 基于角色的访问控制模型

**决策日期**：2026-07-25

**决策人**：Architect

### 决策点 2：选择【A - Permission Middleware】

**决策**：选择中间件层面的权限校验

**决策日期**：2026-07-25

**决策人**：Architect

### 决策点 3：选择【B + C - 权限点路由控制 + 后端返回菜单（混合）】

**决策**：前端使用权限点列表动态过滤路由 + 后端返回菜单结构

**决策日期**：2026-07-25

**决策人**：Architect

## 7. Why

### 决定因素分析

#### RBAC

| 因素 | RBAC | ABAC | 说明 |
|------|------|------|------|
| 满足 PRD 需求 | ✅ 完全满足 | ❌ 过度设计 | PRD 只需要功能级权限，不需要属性条件 |
| 实现复杂度 | 简单（3 张表） | 复杂（规则引擎） | RBAC 三张表即可完成 |
| 维护成本 | 低（可视化勾选） | 高（需专人维护规则） | Admin 可通过 UI 勾选权限 |
| 扩展性 | 中（可叠加 ABAC） | 高 | 未来需要数据级权限时可叠加 |

**决定性理由**：
1. **需求匹配**：PRD 仅要求功能级权限控制（Admin/Student 两种角色 + 自定义角色），B 方案属于 ABAC 属于过度设计
2. **实现简单**：roles / permissions / role_permissions 三张表即可，CRUD 逻辑清晰
3. **管理友好**：Admin 可通过复选框界面配置角色权限，学习成本低
4. **未来可扩展**：如果需要数据级权限（如"只能查看本组学生"），可在 RBAC 基础上叠加 ABAC Policy Engine

#### Permission Middleware

| 因素 | Middleware | Service 层 | 说明 |
|------|-----------|------------|------|
| 代码侵入性 | ❌ 无侵入 | ⚠️ 侵入业务 | Middleware 与业务逻辑完全解耦 |
| 安全性 | ✅ 全局覆盖 | ⚠️ 可能遗漏 | Middleware 自动拦截所有匹配路由 |
| 灵活性 | ⚠️ 无法访问业务上下文 | ✅ 可访问 | 但功能权限校验不需要业务上下文 |
| 可维护性 | ✅ 集中管理 | ⚠️ 分散在多个 Service | 权限路由表在一个地方配置 |

**决定性理由**：
1. **关注点分离**：权限是横切关注点，Middleware 是最自然的实现方式
2. **安全不漏**：路由注册时手动声明权限码，如果忘记声明则默认拒绝（fail-safe）
3. **遵循现有模式**：现有代码已有 AuthMiddleware 模式，PermissionMiddleware 可复用同样模式
4. **性能开销极低**：缓存命中时，权限校验在微秒级

#### 前端权限控制策略

**选择 B（权限点路由控制）作为主要策略 + C（后端返回菜单）作为辅助**：

- **权限点路由控制**：登录时后端返回用户的所有权限码列表，前端根据权限码动态渲染路由和菜单
- **后端返回菜单**：后端可以提供 `/api/v1/auth/menus` 接口，返回当前用户可访问的菜单树
- 对于 Student/Admin 两种主要角色，前端也可直接根据 `role` 字段决定默认路由表（快速实现 MVP）

**决定性理由**：
1. **灵活性**：支持自定义角色，权限码方式天然适配
2. **安全性**：后端始终是最终的安全边界，前端控制仅为用户体验优化
3. **开发效率**：MVP 阶段可直接用 role 判断，后续轻松迁移到权限码模式

### 与约束的匹配

| 约束 | 满足情况 | 说明 |
|------|---------|------|
| Admin 和 Student 两种内置角色 | ✅ | 种子数据创建，is_system 保护 |
| Admin 可自定义角色 | ✅ | role CRUD，非 system 角色可删除 |
| 所有受保护接口有权限校验 | ✅ | PermissionMiddleware + 路由声明的权限码 |
| 前端根据角色展示不同页面 | ✅ | 权限码列表控制前端路由 |
| 权限校验不通过返回 403 | ✅ | Middleware 返回 403 |

## 8. Tradeoffs

### 接受的代价

| 代价 | 影响 | 接受理由 |
|------|------|---------|
| RBAC 不支持属性级条件 | 无法实现"仅查看本组数据" | 当前 PRD 不需要，未来可叠加 ABAC |
| Middleware 无法访问请求体 | 无法实现基于请求体的权限判断 | 功能权限不依赖请求体内容 |
| 路由-权限映射表需手动维护 | 新增接口时需要额外配权限码 | 集中在一个地方配置，不易遗漏 |

### 放弃的优势

- **放弃了 ABAC 的灵活性**：因为 PRD 不需要数据级权限
- **放弃了 Service 层校验的上下文访问能力**：因为功能权限校验不需要业务上下文
- **放弃了纯角色路由隔离的简单性**：因为需要支持自定义角色

---

## 9. Consequences

### 正面后果

- 权限体系结构清晰，易于理解和维护
- 新增接口时只需在路由注册处添加权限码声明
- Middleware 拦截确保安全无遗漏
- 前端和后端权限控制职责明确

### 负面后果

- 需要维护路由-权限码映射表
- 自定义角色场景下，权限变更需要前端同步更新
- 新增权限码需要同步添加到种子数据

### 迁移方案

- 为现有 Admin 用户设置默认 Admin 角色（Migration 006 迁移脚本）
- 登录接口返回新增 `role` 字段和 `permissions` 列表
- 现有 API 接口逐步添加权限 Middleware
