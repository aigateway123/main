## 2. Context

### 业务背景

AI Gateway 需要支持按学生 API 调用量自动计费并扣减额度。教育场景下，多个学生可能同时调用 API，存在并发扣费场景。核心要求：
- 扣费后额度不能为负
- 费用计算精确（保留 6 位小数）
- 并发扣费不出现超扣

### 技术背景

- 后端使用 Go 1.22+，PostgreSQL 15+
- 当前为单体服务，后续可能拆分为独立 Billing Service
- 事务内需要完成：定价查询 → 费用计算 → 额度扣减 → 交易记录插入
- 计费必须在 API 调用完成后同步完成（用户需要准确知道扣费结果）

---

## 3. Problem

在保证扣费准确性和并发安全的前提下，选择何种扣费策略和并发控制方案？

### 问题描述

需要决策两个关键点：
1. **扣费时机**：API 调用完成后同步扣费 vs 异步（事件队列）扣费
2. **并发控制**：使用数据库行锁（SELECT FOR UPDATE）vs 乐观锁（version 字段）

### 问题影响

| 影响方面 | 说明 |
|---------|------|
| 功能 | 扣费准确性直接影响平台财务 |
| 性能 | 扣费操作在主链路中，延迟敏感 |
| 成本 | 不同方案对数据库资源消耗不同 |
| 开发效率 | 方案复杂度直接影响实现周期 |

---

## 4. Constraints

| # | 约束 | 类型 | 说明 |
|---|------|------|------|
| 1 | 扣费后额度不能为负 | 业务 | 不允许超支，平台承担损失 |
| 2 | 并发扣费数据一致性 | 业务 | 同一用户并发请求不出现超扣 |
| 3 | 扣费延迟 < 50ms | 性能 | 99% 的扣费操作在 50ms 内完成 |
| 4 | 费用精度 decimal(16,6) | 业务 | 保留 6 位小数 |

### 不可妥协的约束

- 扣费后额度不能为负
- 数据最终一致性必须保证

### 可协商的约束

- 扣费延迟可以适当放宽（< 100ms 也可接受）

---

## 5. Options

### Option A: 同步扣费 + SELECT FOR UPDATE 行锁

| # | 方案名称 | 描述 | 优点 | 缺点 | 可行性 |
|---|---------|------|------|------|:------:|
| A | 同步扣费 + 行锁 | 在 API 调用完成后，开启数据库事务，使用 SELECT FOR UPDATE 锁定用户行，扣减额度，插入交易记录，提交事务 | 实现简单、强一致性、额度不会超扣 | 行锁影响并发吞吐、事务时间较长 | 高 |
| B | 同步扣费 + 乐观锁 | 每次扣费时使用 UPDATE ... WHERE quota_balance >= cost AND version = old_version，通过版本号或条件判断控制并发 | 无锁、并发吞吐高 | 高并发下重试率高、实现复杂（需重试机制） | 中 |
| C | 异步扣费 + 事件队列 | API 调用完成后直接返回，将计费事件发送到队列，由消费者异步处理扣费 | 主链路延迟低、峰值削峰 | 实时余额不准、用户可能在余额不足时继续调用 | 低 |

---

## 6. Decision

**决策**：选择 Option A — 同步扣费 + SELECT FOR UPDATE 行锁

**决策日期**：2026-07-25

**决策人**：Architect

---

## 7. Why

### 决定性因素

| 因素 | 本方案 | 其他方案 | 说明 |
|------|--------|---------|------|
| 数据一致性 | 强一致、无超扣 | Option B 高并发下有竞争失败；Option C 有窗口期 | 财务数据必须强一致 |
| 实现复杂度 | 低（标准事务） | Option B 需重试逻辑；Option C 需队列基础设施 | MVP 阶段选择简单方案 |
| 实时余额 | 即时准确 | Option C 有延迟 | 学生需要实时查看余额 |
| 安全性 | 行锁保证不超扣 | Option B 条件 UPDATE 也可能超扣（需额外校验） | 行锁是最成熟的方案 |

### 与约束的匹配

| 约束 | 满足情况 | 说明 |
|------|---------|------|
| 扣费后额度不能为负 | ✅ | 事务内先查后扣，余额不足回滚 |
| 并发扣费一致性 | ✅ | FOR UPDATE 行锁保证串行化 |
| 扣费延迟 < 50ms | ✅ | 单行操作 + 短事务，通常 < 10ms |

---

## 8. Tradeoffs

### 接受的代价

| 代价 | 影响 | 接受理由 |
|------|------|---------|
| 行锁影响并发 | 同一用户并发扣费串行化 | 教育场景下并发度不高，且事务极短（< 10ms） |
| 事务时间敏感 | 事务内不能有外部 API 调用 | 定价查询提前完成，事务内仅做 DB 操作 |
| 数据库连接占用 | 事务期间占用一个连接 | 连接池充足，短事务影响可控 |

### 放弃的优势

- 放弃了 Option B 的「高并发吞吐」优势，因为教育场景不需要极高的并发扣费
- 放弃了 Option C 的「低延迟」优势，因为实时余额是产品核心需求

---

## 9. Consequences

### 正面后果

- 扣费逻辑简单可靠，易于实现和调试
- 数据强一致性，财务记录准确
- 开发者容易理解和维护

### 负面后果

- 同一用户的 API 调用在扣费阶段串行化（行锁等待）
- 事务必须保持简短，不能混入外部调用

### 迁移方案

无迁移需求，此为新建功能。

---

## 10. Risks

| # | 风险描述 | 等级 | 可能性 | 影响 | 缓解方案 |
|---|---------|------|--------|------|---------|
| 1 | 事务死锁 | 中 | 低 | 事务回滚 | 统一加锁顺序（先用户后交易），设置锁超时 |
| 2 | 长事务阻塞 | 中 | 低 | 影响其他用户 | 事务内仅做 DB 操作，不超过 50ms |
| 3 | 应用层重试导致重复扣费 | 中 | 中 | 多扣费 | 使用 reference_id 做幂等，唯一索引约束 |

---

## 11. Alternatives

| 方案 | 未选原因 | 未来可行性 |
|------|---------|:----------:|
| 异步扣费 + 事件队列 | 实时余额不满足产品需求 | 高（后续可扩展为异步对账通道） |
| 乐观锁 + 重试 | 实现复杂，且教育场景并发不高，无需额外复杂度 | 中（高并发场景可考虑） |

# ADR-002: RBAC 实现方式（中间件+数据库 vs 硬编码）

Version: v1.0

Last Updated: 2026-07-25

---

## 1. Metadata

| 字段 | 值 |
|------|-----|
| ADR ID | ADR-002 |
| Title | RBAC 实现方式（中间件+数据库 vs 硬编码） |
| Version | v1.0 |
| Status | Accepted |
| Owner | Architect |
| Related PRD | PRD-20260725-001 |
| Related Architecture | ARCH-20260725-Student-Billing-RBAC |
| Created | 2026-07-25 |
| Last Updated | 2026-07-25 |

---

## 2. Context

### 业务背景

需要支持 Admin 和 Student 两种角色，以及后续扩展的自定义角色。不同角色拥有不同的功能权限（如：学生不能管理 Provider/Model）。Admin 需要能在后台动态分配权限。

### 技术背景

- 当前路由通过 `http.ServeMux` + 中间件链管理
- AuthMiddleware 已验证 JWT Token，将 userID/email 放入 Context
- 新增权限校验中间件需要在 AuthMiddleware 之后执行

---

## 3. Problem

如何实现 RBAC 权限校验，使其既满足 MVP 快速交付，又支持未来灵活扩展？

### 问题描述

| 影响方面 | 说明 |
|---------|------|
| 功能 | 权限校验覆盖所有受保护 API |
| 性能 | 权限校验在主链路中，需低延迟 |
| 可维护性 | 权限变更不应需要代码部署 |
| 可扩展性 | 支持自定义角色和权限 |

---

## 4. Constraints

| # | 约束 | 类型 | 说明 |
|---|------|------|------|
| 1 | 权限变更即时生效 | 业务 | Admin 修改角色权限后无需重启服务 |
| 2 | 权限校验 < 20ms | 性能 | 包含 Redis 缓存未命中场景 |
| 3 | 支持自定义角色 | 业务 | Admin 可创建/编辑/删除角色 |
| 4 | 向后兼容 | 技术 | 现有 Admin 用户自动拥有全部权限 |

---

## 5. Options

| # | 方案名称 | 描述 | 优点 | 缺点 | 可行性 |
|---|---------|------|------|------|:------:|
| A | 数据库 RBAC + Redis 缓存 + 中间件 | 权限数据存储在 DB，提供 RBACService 供中间件调用，Redis 缓存加速 | 灵活、权限变更即时、缓存加速、标准的 RBAC 模式 | 需要维护缓存一致性 | 高 |
| B | 硬编码权限（代码中写死） | 在 Service/Controller 中直接 hardcode 权限检查 | 实现最快、无额外查询 | 不支持动态变更、每次改权限需部署 | 中 |
| C | Casbin 集成 | 使用 Casbin 作为权限引擎 | 功能强大、支持多种模型 | 引入外部依赖、学习成本高、对 MVP 过重 | 中 |

---

## 6. Decision

**决策**：选择 Option A — 数据库 RBAC + Redis 缓存 + 中间件

**决策日期**：2026-07-25

**决策人**：Architect

---

## 7. Why

### 决定性因素

| 因素 | 本方案 | 其他方案 | 说明 |
|------|--------|---------|------|
| 权限动态变更 | ✅ 数据库配置即生效 | Option B 需部署 | 产品核心需求 |
| 实现复杂度 | 中（标准 RBAC + 缓存） | Option B 简单但不可扩展；Option C 复杂 | MVP 和扩展性平衡 |
| 性能 | 缓存命中 < 5ms | Option B 最快但不可维护 | 缓存策略成熟可靠 |
| 可维护性 | 数据结构清晰 | Option C Casbin 学习曲线 | Go 团队熟悉标准 SQL |

### 与约束的匹配

| 约束 | 满足情况 | 说明 |
|------|---------|------|
| 权限变更即时生效 | ✅ | 写入 DB 后清除缓存，下次请求加载 |
| 权限校验 < 20ms | ✅ | 缓存命中 < 5ms，未命中 < 20ms |
| 支持自定义角色 | ✅ | roles 表 + role_permissions 表支持任意角色 |
| 向后兼容 | ✅ | 迁移脚本为现有用户设置 Admin 角色 |

---

## 8. Tradeoffs

### 接受的代价

| 代价 | 影响 | 接受理由 |
|------|------|---------|
| 缓存一致性 | 权限变更后最多有 TTL 窗口期的延迟 | TTL 5 分钟 + 变更时主动清除，接受短时间延迟 |
| 额外的数据库查询 | 冷启动时多一次 JOIN 查询 | 缓存预热后仅查缓存 |
| 中间件链长度增加 | 每个请求多一次权限查询 | 缓存命中时开销极小 |

### 放弃的优势

- 放弃了 Option B 的零额外依赖和极简实现
- 放弃了 Option C 的丰富的策略模型（如 ABAC）

---

## 9. Consequences

### 正面后果

- 权限体系灵活可扩展，支持未来更多角色和权限
- 实现标准 RBAC，团队成员容易理解
- Redis 缓存保证高性能

### 负面后果

- 需要在 main.go 中注册 RBACMiddleware 到受保护路由
- 需要维护缓存与数据库的一致性

### 迁移方案

无需迁移，全部为新建功能。

---

## 10. Risks

| # | 风险描述 | 等级 | 可能性 | 影响 | 缓解方案 |
|---|---------|------|--------|------|---------|
| 1 | 权限遗漏 | 中 | 中 | 越权访问 | 安全评审 checklist 覆盖所有 API |
| 2 | 缓存穿透 | 低 | 低 | 数据库压力增大 | 缓存空值 + Bloom Filter（后续优化） |

---

## 11. Alternatives

| 方案 | 未选原因 | 未来可行性 |
|------|---------|:----------:|
| 硬编码 | 不支持动态权限变更 | 低 |
| Casbin | 对 MVP 过重，增加学习成本 | 中（后续可迁移） |

# ADR-003: 定价策略设计（可配置模型定价 + 峰谷计价支持）

Version: v1.0

Status: Accepted

Owner: Architect

Last Updated: 2026-07-25

---

## 1. Metadata

| 字段 | 值 |
|------|-----|
| ADR ID | ADR-003 |
| Title | 定价策略设计（可配置模型定价 + 峰谷计价支持） |
| Version | v1.0 |
| Status | Accepted |
| Owner | Architect |
| Related PRD | PRD-20260725-001 (FR-17, FR-17.1, FR-18) |
| Related Architecture | ARCH-20260725-Student-Billing-RBAC |
| Created | 2026-07-25 |
| Last Updated | 2026-07-25 |

---

## 2. Context

### 业务背景

不同 AI 模型有不同的调用成本，且部分模型厂商（如 DeepSeek）采用峰谷计价策略（白天/夜间不同价格）。Admin 需要在后台动态配置模型价格，修改后即时生效。

### 技术背景

- 每个模型对应一个定价记录（model_pricing 表）
- 计价发生在 API 调用完成后，根据实际 token 用量计算
- 需要同时支持普通定价（flat rate）和峰谷计价（time-based）

---

## 3. Problem

如何设计模型定价体系，同时支持普通定价和峰谷计价两种模式？

### 问题描述

| 影响方面 | 说明 |
|---------|------|
| 功能 | Admin 可在后台配置每个模型的定价 |
| 性能 | 定价查询在主链路中，需低延迟（< 5ms） |
| 灵活性 | 支持 flat 和 time_based 两种模式 |
| 扩展性 | 后续可能增加更多定价策略（如按量阶梯、套餐） |

---

## 4. Constraints

| # | 约束 | 类型 | 说明 |
|---|------|------|------|
| 1 | 定价不写死，存储在数据库 | 业务 | Admin 后台 CRUD 管理 |
| 2 | 支持峰谷计价（峰/谷两个时段） | 业务 | 如 DeepSeek 白天/夜间不同价格 |
| 3 | 计费根据调用时间自动匹配定价 | 业务 | 峰谷自动判断，无需人工干预 |
| 4 | 费用计算保留 6 位小数 | 业务 | decimal(16,6) |

### 不可妥协的约束

- 定价必须可配置（不硬编码）
- 峰谷计价的时间段判断要正确

### 可协商的约束

- 定价缓存 TTL 可以适当调整（10 分钟以内）

---

## 5. Options

| # | 方案名称 | 描述 | 优点 | 缺点 | 可行性 |
|---|---------|------|------|------|:------:|
| A | 单表 + pricing_type 字段区分 | model_pricing 表包含 flat 和 time_based 的所有字段，通过 pricing_type 区分使用哪种策略 | 简单、一个表搞定、查询快 | 峰谷相关字段在 flat 模式下为空 | 高 |
| B | 双表：定价主表 + 峰谷子表 | model_pricing 存公共字段，model_pricing_time_based 存峰谷时段和价格 | 规范化、扩展性好 | 需要 JOIN 查询，增加复杂度 | 中 |
| C | JSON 字段存储定价策略 | 使用 JSONB 字段存储灵活定价策略 | 最灵活 | 类型安全弱、查询不便、维护困难 | 低 |

---

## 6. Decision

**决策**：选择 Option A — 单表 + pricing_type 字段区分

**决策日期**：2026-07-25

**决策人**：Architect

---

## 7. Why

### 决定性因素

| 因素 | 本方案 | 其他方案 | 说明 |
|------|--------|---------|------|
| 实现复杂度 | 最低 | Option B 需 JOIN；Option C JSON 难维护 | MVP 优先，简单方案 |
| 查询效率 | 一次查询获取全部 | Option B 需 JOIN | 性能敏感链路 |
| 可维护性 | 结构清晰（字段含义明确） | Option C JSON 无 schema | 团队开发效率 |
| 数据完整性 | CHECK 约束保障 | Option C JSON 无约束 | 数据质量 |

### 与约束的匹配

| 约束 | 满足情况 | 说明 |
|------|---------|------|
| 定价不写死 | ✅ | model_pricing 表存储在数据库，Admin CRUD 管理 |
| 支持峰谷计价 | ✅ | pricing_type + peak_start/end + peak/offpeak 价格字段 |
| 自动匹配 | ✅ | 通过比较当前时间与时段判断 |
| 精度 decimal(16,6) | ✅ | 所有价格字段均为 DECIMAL(16,6) |

---

## 8. Tradeoffs

### 接受的代价

| 代价 | 影响 | 接受理由 |
|------|------|---------|
| flat 模式下有冗余字段 | peak/offpeak 字段为 NULL | 字段统一在单表，查询方便 |
| 时段判断逻辑在应用层 | 需要 Go 代码实现 | 数据库函数也可实现，但应用层更灵活可测试 |
| 定价模型有限 | 只支持 flat 和 time_based 两种 | 未来可通过扩展 pricing_type 增加新类型 |

### 放弃的优势

- 放弃了 Option B 的完全规范化设计，但获得了查询效率
- 放弃了 Option C 的极致灵活性，但获得了类型安全和可维护性

---

## 9. Consequences

### 正面后果

- 定价查询单表完成，零 JOIN，性能最优
- CHECK 约束保证 pricing_type 合法
- 新增定价策略只需扩展 CHECK 约束 + 应用层逻辑

### 负面后果

- time_based 模式的字段在 flat 模式下为空，占用少量存储
- 应用层需要实现峰谷时段判断逻辑

### 迁移方案

无迁移需求，此为新建功能。创建模型时同时创建默认定价记录（pricing_type='flat', 价格为 0）。

---

## 10. Risks

| # | 风险描述 | 等级 | 可能性 | 影响 | 缓解方案 |
|---|---------|------|--------|------|---------|
| 1 | 模型缺少定价记录导致计费失败 | 中 | 中 | API 返回 500 | 创建模型时自动插入默认定价；查询时使用 COALESCE |
| 2 | 跨天时段判断错误 | 中 | 低 | 费用计算错误 | 单元测试覆盖跨天场景；日志记录定价匹配结果 |
| 3 | 定价缓存脏数据 | 低 | 低 | 使用旧价格 | Admin 修改定价后主动清除缓存；短 TTL |
