## 2. Product Background

### 行业背景

AI Gateway 作为大模型统一接入平台，Admin 需要全面了解平台的费用收入和使用情况，以便做出运营决策。当前系统已具备基础计费能力（额度管理、扣费、模型定价），但缺乏对历史数据的聚合分析和可视化的报表能力。

在实际运营中，Admin 需要回答以下问题：
- **今天**平台产生了多少费用？
- **这个月**哪些模型消费最多？哪些用户消耗最大？
- **哪个学生**快没额度了？需要充值？
- **整体用量**趋势在上升还是下降？

### 用户需求

- **Admin** 需要一目了然的全平台费用看板，支持按时间维度（日/周/月/自定义）聚合查看费用和用量
- **Admin** 需要按用户、模型维度下钻分析，定位高消费用户和高消耗模型
- **Admin** 需要导出报表用于财务对账和汇报
- **学生**需要查看个人消费明细和趋势，了解自己的 API 使用成本

---

## 3. Problem Statement

当前系统虽然实现了计费扣费的基础能力，但缺少对计费数据的聚合分析和可视化呈现。

| 问题 | 影响 |
|------|------|
| 没有费用总览看板 | Admin 无法快速了解平台整体费用和用量情况 |
| 缺少多维度聚合分析 | 无法按用户、模型、时间等维度分析消费数据 |
| 没有趋势图表 | 无法观察费用的时序变化趋势 |
| 缺少报表导出能力 | 无法导出数据用于财务对账和团队汇报 |
| 学生端缺少用量分析 | 学生只能看到简单余额，看不到消费明细和趋势 |

## 4. Goals

### 产品目标

- **目标 1**：Admin 可在账单报表中心查看全平台费用和用量的总览
- **目标 2**：Admin 可按日/周/月/自定义时间范围查看聚合数据和趋势图
- **目标 3**：Admin 可按用户、模型维度下钻分析消费明细
- **目标 4**：Admin 可导出报表为 CSV/Excel 格式
- **目标 5**：学生端可查看个人消费明细和趋势图

### 非目标

- <ins>本次不做</ins> 自动生成定时邮件报表
- <ins>本次不做</ins> 自定义报表模板
- <ins>本次不做</ins> 成本优化建议（留到 P2 Policy Platform）
- <ins>本次不做</ins> 预算预警与预算管理（留到 P2）
- <ins>本次不做</ins> 多币种报表

## 6. User Story

### 核心用户故事

1. **作为** Admin，**我希望**打开报表中心就看到今天的总收入和请求数等关键指标，**以便**快速了解平台运营状况
2. **作为** Admin，**我希望**查看费用的时序趋势图，**以便**观察变化趋势
3. **作为** Admin，**我希望**按时间范围（日/周/月/自定义）筛选报表，**以便**查看不同周期的经营数据
4. **作为** Admin，**我希望**按用户维度查看消费排行，**以便**识别高消费用户
5. **作为** Admin，**我希望**按模型维度查看消费分布，**以便**评估各模型的使用情况
6. **作为** Admin，**我希望**导出报表为 CSV 文件，**以便**用于财务对账
7. **作为** 学生，**我希望**查看个人消费明细和趋势，**以便**了解自己的 API 使用成本

## 9. User Flow

### 主流程 1：Admin 查看经营总览

```
Admin 登录 → 导航到「账单报表」
    │
    ▼
进入报表首页
    │
    ▼
系统加载：今日收入/今日请求数 + 本月收入/本月请求数
    │
    ▼
Admin 切换时间范围（今日 / 昨日 / 近7天 / 本月 / 自定义）
    │
    ▼
系统更新所有卡片和趋势图数据
    │
    ▼
Admin 可查看：
├── 折线图：收入趋势
├── 饼图：各模型消费占比
├── 表格：各模型用量详情
├── 排行：用户消费 TopN
└── 表格：用户消费明细
```

### 主流程 2：Admin 导出报表

```
Admin 在报表页设置筛选条件（时间范围）
    │
    ▼
点击「导出」按钮
    │
    ▼
选择导出格式（CSV / Excel）
    │
    ▼
系统生成文件 → 自动下载
```

### 主流程 3：学生查看个人消费

```
学生登录 → 导航到「用量明细」
    │
    ▼
查看个人消费总览卡片（今日 / 本月 / 总计）
    │
    ▼
查看近 7 天消费趋势图
    │
    ▼
查看消费明细列表（支持日期筛选和分页）
```

### 异常流程

| 异常场景 | 处理方式 |
|---------|---------|
| 所选时间范围内无数据 | 显示「暂无数据」空状态，图表展示为空 |
| 报表数据量过大导致查询超时 | 后端自动聚合，返回聚合数据而非原始明细 |
| 导出失败（如磁盘空间不足） | 前端提示「导出失败，请稍后重试」 |
| 计费数据尚未生成（如当天未结束） | 显示「数据截至当前时间」提示 |

## 12. Database Impact

| 表名 | 变更类型 | 说明 |
|------|---------|------|
| `request_logs` | 无变更 | 报表查询主要依赖此表 |
| `quota_transactions` | 无变更 | 额度交易记录，用于交叉验证 |
| `billing_daily_stats` | **新增** | 每日聚合统计表，加速报表查询 |

### 新增表：billing_daily_stats

```sql
CREATE TABLE billing_daily_stats (
    id              BIGSERIAL PRIMARY KEY,
    stat_date       DATE            NOT NULL,           -- 统计日期
    user_id         BIGINT          NOT NULL,           -- 用户 ID
    model_id        BIGINT          NOT NULL,           -- 模型 ID
    request_count   INTEGER         NOT NULL DEFAULT 0, -- 请求次数
    input_tokens    BIGINT          NOT NULL DEFAULT 0, -- 输入 Token
    output_tokens   BIGINT          NOT NULL DEFAULT 0, -- 输出 Token
    total_revenue   DECIMAL(18,6)   NOT NULL DEFAULT 0, -- 总收入（用户扣费金额）
    created_at      TIMESTAMP       NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMP       NOT NULL DEFAULT NOW(),
    
    -- 联合唯一约束：每天每用户每模型一条记录
    UNIQUE(stat_date, user_id, model_id)
);

-- 查询索引
CREATE INDEX idx_bds_stat_date ON billing_daily_stats(stat_date);
CREATE INDEX idx_bds_user_id ON billing_daily_stats(user_id);
CREATE INDEX idx_bds_model_id ON billing_daily_stats(model_id);

-- 复合索引：时间范围 + 用户维度查询
CREATE INDEX idx_bds_date_user ON billing_daily_stats(stat_date, user_id);
-- 复合索引：时间范围 + 模型维度查询
CREATE INDEX idx_bds_date_model ON billing_daily_stats(stat_date, model_id);
```

### 聚合策略

- 每天凌晨异步计算前一天的 `billing_daily_stats` 聚合数据
- 报表查询优先读取聚合表，当日数据实时从 `request_logs` 计算
- 聚合表支持快速查询任意时间范围的数据，避免全表扫描

## 13. Risks

| # | 风险描述 | 等级 | 可能性 | 影响 | 缓解方案 |
|---|---------|------|--------|------|---------|
| 1 | `request_logs` 表数据量大，实时聚合查询慢 | 高 | 高 | 报表加载慢 | 使用 `billing_daily_stats` 聚合表 + 索引优化 |
| 2 | 当日实时数据与聚合表数据不一致 | 中 | 中 | 数据准确性 | 聚合表每日增量更新，当日数据实时查 + 聚合表兜底 |
| 3 | 导出大范围数据超时 | 中 | 中 | 导出失败 | 限制最大导出范围（默认最近 3 个月），超限走异步生成 |
| 4 | 收入计算口径不一致 | 高 | 低 | 报表数据错误 | 统一使用 `request_logs.cost_amount` 作为数据源，公式保持一致 |
