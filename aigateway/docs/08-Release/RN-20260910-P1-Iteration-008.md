## 3. ⚠️ 行为变更与升级须知

| 变更 | 影响 | 升级动作 |
|------|------|----------|
| Anthropic 入站不再自动服务「仅配 OpenAI 端点」的 Provider | 此前靠跨协议转换能跑通的 `/v1/messages` 调用，升级后会直接返回 **503 `overloaded_error`** | 上线前为需要支持 `/v1/messages` 的 Provider 补齐 Anthropic 端点，否则先不要切流 |
| 请求体不再跨协议改写 | 上游 Provider 将收到与客户端完全一致的请求体（字段名、`system` 形态等） | 上游必须真实支持该协议的官方契约 |
| 响应体不再跨协议改写 | Anthropic 入站返回 Anthropic 原生响应结构 | 客户端按各自 SDK 正常解析即可（#006/#007 起已支持） |
| 存量 `protocol_type='anthropic'` Provider 的 `base_url` 等列被清空、值搬至 `anthropic_*` | 直接查库/脚本读取 `base_url` 的运维流程会读到空值 | 迁移前先备份 `providers` 表 |
| `binding.api_path_override` 仅对 OpenAI 入站生效 | 双协议 Provider 的 Anthropic 出站路径固定取 `anthropic_api_path` | 无（修复项，避免路径被污染） |

3. **不做协议转换**：这是本迭代的设计取舍（严格模式）；`chat_adapter.go` 转换器代码保留但不再挂载到路由链路，未来如需恢复可加开关。
4. **`anthropic_api_path` 列默认值**：非 Anthropic Provider 该列为 `'/v1/messages'`（因 `anthropic_base_url` 为空而不参与路由）。
5. **图片生成链路未纳入**：`image_service.go` 仍按 OpenAI 兼容端点直连，未做双协议改造（保持原有行为）。
6. **迁移版本号唯一性隐患**：`20260910_014_*` 的 version 前缀解析为 `20260910`，同日第二个迁移会被迁移器静默跳过（已实测复现）。后续迁移请使用 `YYYYMMDDNNNN_` 命名（如 `202609100014_`）；`down.sql` 的 `DELETE FROM schema_migrations` 语句与版本号字符串绑定，重命名迁移文件时需同步更新。

## 7. 回滚预案

| 场景 | 操作 |
|------|------|
| 迁移前（必做） | 备份 `providers` 表：`CREATE TABLE providers_bak_YYYYMMDD AS SELECT * FROM providers;`（迁移会清空存量 anthropic Provider 的 `base_url` / `api_path` / `api_key_ref`，不可逆） |
| 迁移异常 | 执行 `20260910_014_...down.sql`（会删除 4 列并清理 `schema_migrations`，使重新升级可正常执行）；已搬运的端点数据需按下方顺序人工恢复 |
| 回滚后重新升级 | 重启 gateway 即由迁移器重新应用 014（`down.sql` 已清理版本记录）；注意：重新升级**不会**自动恢复端点数据，且会以已清空的 `base_url` 覆写 `anthropic_*`，因此**恢复必须在重新升级之后**执行 |
| 端点数据恢复 | `UPDATE providers p SET anthropic_base_url = b.anthropic_base_url, anthropic_api_path = b.anthropic_api_path, anthropic_api_key_ref = b.anthropic_api_key_ref, anthropic_auth_type = b.anthropic_auth_type FROM providers_bak_YYYYMMDD b WHERE p.id = b.id;`（已验证可用） |
| 路由行为异常 | 回退 gateway 二进制至上一版本（无需回滚 DB：新增列可空且旧版本忽略） |
| 客户端 503 激增 | 属预期的严格模式行为，优先为相关 Provider 补配 Anthropic 端点；紧急可先回退 gateway 版本 |
| Admin 表单异常 | 回退 admin 镜像 |

> ⚠️ 回滚禁止手工删除 `schema_migrations` 记录或手工执行 `up.sql`：`up.sql` 非幂等（`ADD COLUMN` 无 `IF NOT EXISTS`），处于「列存在但无版本记录」中间态时迁移器会报 `column "anthropic_base_url" ... already exists` 并退出（已实测复现）。

### 9.1 OpenAI 端点认证方式可配置【P0】

| # | 内容 | 状态 |
|:-:|------|:----:|
| 1 | `auth_type` 语义明确为 **OpenAI 端点认证方式**：`bearer` → `Authorization: Bearer <key>`；`api_key` → `x-api-key: <key>` | ✅ |
| 2 | 后端 `endpointForProtocol` 的 OpenAI 分支不再硬编码 `bearer`，改为读取 `auth_type`（空值回退 `bearer`）；`CallProvider` 按该值写对应请求头 | ✅ |

**⚠️ 存量数据必须与代码同时上线**：迁移 013 给 `auth_type` 设的默认值是 `'api_key'`，且 Iteration #006 的 Admin 在非 Anthropic 时强制写入 `authType='api_key'`。旧代码忽略该列、硬编码 Bearer，问题一直被掩盖；若只升级代码不修数据，存量 OpenAI Provider 会从 Bearer 变为 `x-api-key` → **线上调用全线 401**。修复由三处共同构成（缺一不可）：迁移 015 改列默认值 + 修正存量数据 + 后端按端点推导默认值。

### 9.3 新增接口 `POST /api/v1/providers/test-endpoint`

| 项 | 内容 |
|----|------|
| 权限 | `admin:provider:manage`（与 Provider 增删改一致；RBAC 按 `/api/v1/providers` 前缀 + 非 GET 自动继承，中间件无需改动） |

| 限制 | 仅确认「网络可达 + 认证被接受」，不代表模型可用（不发推理请求）；不做内网地址黑名单（`base_url` 本允许私有部署中转，接口权限与增删改同级），SSRF 为已知限制 |

### 9.5 部署脚本适配

- `infra/scripts/lib.sh`：迁移改为 `MIGRATIONS` 数组 + 参数化 `migration_file <基名> up|down`、`migration_version <基名>`；`verify_migration` 逐迁移核对版本记录，并新增 015 专属断言（`auth_type` 列默认值为 `bearer`、`protocol_type='openai' AND base_url<>'' AND auth_type='api_key'` 的行数为 0）。
- `infra/scripts/rollback.sh`：`down_file` 显式取 `MIGRATION_014`，仅回滚 014。
- `infra/scripts/deploy.sh`：调用点不变（`verify_migration` 内部已遍历），`migration_done` 判定仍依据 `anthropic_base_url` 列存在与否。
- **上线时发现并修复脚本两处缺陷（首次在服务器实跑才暴露）**：
  1. `resolve_compose_file` 默认取 `infra/docker/docker-compose.yml`，而生产运行的 gateway / admin / postgres 由**仓库根目录** `docker-compose.yml` 编排（compose 项目名 `aigateway`；`infra/docker` 那份项目名为 `docker`，仅用于 portal）。原默认值会使 `docker compose ps` 查不到 postgres 容器，脚本直接以「postgres 容器未运行」退出 → 改为默认取仓库根目录文件，`infra/docker` 那份作为兜底，仍可用 `COMPOSE_FILE` 覆盖。
  2. `backup_providers` 中 `local suffix="$1" bak="providers_bak_${suffix}"`：`set -u` 下 bash 在赋值前就展开 `${suffix}`，报 `suffix: unbound variable`，导致备份步骤必失败 → 拆成两条 `local`。
